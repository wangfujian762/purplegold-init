# RULES · 紫金规范操作手册

> 本文件是紫金规范在此项目中的蒸馏规则，供 AI Agent 阅读与执行。
> 人类工程师的确认是多个流程节点的必要条件，凡条目中写明"经人类工程师确认"的，不得由 AI 自行替代。

## 1. 项目结构

```
<项目根>/
├── AGENTS.md       # AI 入口指针（指向本文件）
├── purplegold/     # 静态规则层：紫金规范的规则，只在升级紫金规范版本时变化
│   ├── VERSION     # 本项目使用的紫金规范版本
│   ├── RULES.md    # 本文件
│   ├── templates/  # 合金文档模板（ALLOY.template.md、ALLOY.root.template.md）
│   ├── scripts/    # align.py（对齐脚本）、validate.py（校验脚本）
│   ├── 脊椎规范/    # 脊椎流程各阶段的规范，每阶段一个文件夹（含 规范.md），以"类字母 S+两位数字-名称"命名（S01 至 S08）
│   └── 肋骨规范/    # 各肋骨规范的定义，每份规范一个文件夹（含 规范.md，可携带参数文件等附件），以"类字母+两位数字-名称"编号命名；预置十三份初始规范（见第 4 节）
├── 紫金产物/        # 动态文档层：项目产出的文档
│   ├── 紫金规范反馈.md  # 紫金规范缺陷与建议（实例到本体的反馈通道）
│   ├── 脊椎产物/    # 脊椎流程各阶段的产出文档，每阶段一个文件夹（初始化时为空，随首次产出创建）
│   └── 肋骨产物/    # 各肋骨规范的执行产出，每份规范一个文件夹
│       └── AB03-项目最新状态/  # 例外：随实例模板预置（含三份状态文档骨架，见第 5 节）；其余规范文件夹初始化时不预建，随首次产出创建
└── project/        # 工程根：项目的模块树，合金文档共置其中
    └── ALLOY.md    # 根模块合金文档（含派生区）
```

- 除合金文档外，项目的一切文档只放在 `purplegold/`（规则）或 `紫金产物/`（产物）中。
- `purplegold/` 与 `紫金产物/` 下的任何内容都不是模块；模块概念只作用于 `project/` 路径之下。

## 2. 外骨骼：合金文档体系

### 2.1 模块认定

- 模块 = 工程中扮演独立角色的单位，分文件夹模块与单文件模块两种形态。判定不设统一标准，以高内聚、低耦合、单向依赖为准；但一旦某文件或文件夹需要命名、需要进入依赖图、或需要参与边界关系，就必须认定为模块。
- 文件夹模块有且仅有一份合金文档：模块文件夹内的 `ALLOY.md`。单文件模块没有合金文档，其命名登记在父模块的"子模块指针"中。
- 非模块内容（普通文件、纯容器文件夹）不命名、不进图、不登记；非模块文件夹的整个子树内不得出现 `ALLOY.md`。

### 2.2 标准阅读流程

修改或深入理解模块 A 之前，必须依次阅读：

1. A 的合金文档（`A 的路径/ALLOY.md`）；
2. A 的父模块合金文档中的"内部关系"一节——A 与同级模块的依赖关系只记载在那里；
3. 需要全局视图时，读根模块合金文档（`project/ALLOY.md`）派生区的"全工程模块索引""内部关系总览""全工程边界总览""接口与行为约定总览"。

### 2.3 同步原则

- 更新模块之前，必须先更新其所对偶的合金文档；更新合金文档之后，必须考虑是否要更新对应的模块。二者同时存在、同时消失。
- 架构发生变化时，所有受影响的合金文档同步重构；模块移动或删除时，其对偶合金文档随之移动或删除。

### 2.4 合金文档格式（硬要求）

- 以固定格式开头：H1 命名行 `# 合金文档 · <命名>`，下一行是时间戳行 `> 最后修改：YYYY-MM-DD HH:MM:SS`（每次修改文档时更新）。
- 七个必备 H2 小节，标题固定：模块简介、子模块指针、内部关系、边界关系、父模块指针、接口与行为约定、其他信息。"接口与行为约定"记录模块间的调用契约（由提供方模块记录，内容不限固定格式）；无约定时写"（无。）"。
- 指针列表项格式：``- `路径` · 命名 — 说明``；边界关系为 `- 成员命名 — 外部对象 — 交互说明`。路径一律为项目根相对路径，以 `/` 结尾表示文件夹模块，否则表示单文件模块。
- 内部关系的 mermaid 图是依赖关系的唯一权威表征：只使用 `graph TD` 开头、每行一条 `X --> Y` 的严格子集，节点使用子模块的命名。
- 依赖只允许发生在同级模块之间（同一父模块的子模块之间），必须无环；跨层级的依赖改为父模块之间的依赖来表达。
- 命名不得包含空格、`.`、`/`、`\`、`-->`；同一父模块下的子模块不得重名。
- 白名单制：必备小节之外可自由添加任何内容，脚本忽略其不认识的部分。
- 编写新模块的合金文档时，复制 `purplegold/templates/` 下的模板（普通模块用 `ALLOY.template.md`，根模块用 `ALLOY.root.template.md`）填写，成品文件名固定为 `ALLOY.md`。

### 2.5 脚本

- 每次修改合金文档之后，运行对齐脚本 `python3 purplegold/scripts/align.py`：重新生成根模块 `ALLOY.md` 的派生区（含聚合各模块"接口与行为约定"小节的"接口与行为约定总览"）。派生区（标记线 `<!-- 派生区 · … -->` 以下）禁止手工编辑。
- 提交或阶段收尾前，运行校验脚本 `python3 purplegold/scripts/validate.py`。校验不通过时先修复，再继续后续工作。校验项清单：
  - 文件夹模块与 `ALLOY.md` 一一对应：每个文件夹模块有且仅有一份 `ALLOY.md`；凡含 `ALLOY.md` 的文件夹必须被其父模块登记为子模块；
  - 非模块文件夹的子树内不得出现 `ALLOY.md`（模块的祖先必须全是模块）；
  - 每份合金文档的 H1 命名行、时间戳行与必备小节齐全、格式合规；其中"接口与行为约定"小节只检查存在性，不检查内容格式；
  - 命名合规：同一父模块下的子模块不重名；子模块指针中的命名与目标文件夹模块的 H1 命名一致；
  - 父模块指针、子模块指针与实际目录一致；文档声明的模块路径与实际位置一致；
  - 凡出现在内部关系图与边界关系中的成员，必须都是已登记的子模块（以命名核对）；依赖关系无环；
  - 边界关系列表项格式合规（内容是否属实无法机器检查，靠人工维护）；
  - 根模块派生区与各局部合金文档处于对齐状态；
  - 实例骨架就位：`紫金产物/紫金规范反馈.md`、`purplegold/VERSION`、`紫金产物/肋骨产物/AB03-项目最新状态/` 的三份状态文档（脊椎流程进展、肋骨规范进展、外骨骼实现情况）。

## 3. 内骨骼：脊椎流程

脊椎流程是项目前期设计工作的主线，八个阶段按顺序推进：

| 序号 | 阶段 | 产物（按顺序排列） |
|---|---|---|
| S01 | 需求确认 | 需求确认清单、约束与非功能需求、用户角色定义、业务术语表 |
| S02 | 功能初步设计 | 功能清单、业务流程描述、范围声明（可选：用例集） |
| S03 | 功能交互设计 | 页面清单、页面流转图、逐页交互描述、用户操作路径、异常与空态规则 |
| S04 | UI 视觉设计 | UI 设计需求（可选）、视觉稿、设计规范、组件清单、素材清单 |
| S05 | 工程架构与契约 | 技术选型说明、模块架构设计文档、数据模型设计、接口与行为约定（写入各模块合金文档必备小节）、外部服务接入清单、`project/` 下的实施与实施记录 |
| S06 | 制定开发计划 | 任务分解清单、任务顺序与里程碑、任务完成判据、分工说明（可选：风险清单） |
| S07 | 开发和测试 | 代码（`project/` 下）、工程测试记录（单元/集成测试）、偏差记录 |
| S08 | 实机测试和验收 | 实机测试计划、用例库、实机测试报告（含截图）、缺陷清单、验收对照表 |

- 各阶段的规范读 `purplegold/脊椎规范/<阶段文件夹>/规范.md`；产出文档写入 `紫金产物/脊椎产物/<阶段文件夹>/`。两侧阶段文件夹同名，格式为 `S01-需求确认/` 式（S 为脊椎流程的类字母，与肋骨规范的类字母对齐）。初始化时 `紫金产物/脊椎产物/` 为空（仅一个 `.gitkeep` 占位）；阶段文件夹不预建，在首次产出该阶段文档时创建。
- **产物顺序与命名**：各阶段规范中的产物清单按产出的推荐顺序排列，序号（01、02……）在清单中确定，可选产物同样占号。落在阶段产物文件夹内的产物，文件与文件夹一律以 `序号-名称` 命名（如 `01-需求确认清单.md`、`02-视觉稿/`）。承载位置不在阶段产物文件夹内的产物（S05 的接口与行为约定写入各模块合金文档、S07 的代码在 `project/` 下）不参与序号命名，在清单中注明承载位置。
- 上表只列产物名；各产物的内容说明以 `purplegold/脊椎规范/<阶段文件夹>/规范.md` 的产物清单为准。
- **脊椎流程是项目的根本驱动力**：`紫金产物/肋骨产物/AB03-项目最新状态/脊椎流程进展.md` 中登记的脊椎流程进展就是整个项目的宏观待办清单。推进项目 = 推进脊椎流程的当前阶段；开始任何工作前，先依据该文件确认当前处于哪个阶段、该阶段要求什么产物。
- **通用完成判据**：产物清单中的必备产物全部产出（标注"可选"的除外），内容符合各自的内容说明，并经人类工程师确认；各阶段规范在此之上补充特有判据。阶段 S08 的测试在真实已部署的服务上进行。
- **回流条款**：任何阶段的产物都允许修改；一旦任何一个阶段的产物发生变化，须按阶段顺序依次检查其余各阶段的产物是否需要相应修改，检查结论并入当次变更记录（触发时机见第 4 节 AB04-脊椎产物变更记录）。
- **修复缺陷类要求不计入需求文档**：修复缺陷类的要求不构成需求描述，不登记为需求条目——不进入 AF02-需求基线（需求总表及其变更记录）、需求确认清单、UI 设计需求等需求文档。
- 第 6、7、8 阶段（S06～S08）中对模块设计的变更，作为第 5 阶段（S05）的产出处理：更新 `紫金产物/脊椎产物/S05-工程架构与契约/` 内的模块架构设计文档，在 `project/` 下实施，实施记录保留在 S05 产物文件夹内。此类变更同时触发第 2.3 节的合金文档重构。

## 4. 内骨骼：肋骨规范

- 肋骨规范是灵活规范的集合——它不像脊椎流程那样按固定顺序线性推进，而是在特定时机必须适用、或由人类工程师按需启用的规则。规范定义读 `purplegold/肋骨规范/<规范文件夹>/规范.md`；执行产出写入 `紫金产物/肋骨产物/<规范文件夹>/`。初始化时 `紫金产物/肋骨产物/` 仅含预置的 `AB03-项目最新状态/`（见第 5 节）；其余规范文件夹不预建，在首次产出时创建，与规范侧同名（含编号）。
- 分工原则：脊椎是一次性线性建造主线；前置准备、反应式、条件式、重复发生的工作归肋骨规范。
- **按需选用**：肋骨规范可按需选用——实例可裁剪、停用预置规范，也可新增自定义规范；各规范相互独立、互不为前提。
- **触发时机分类**：肋骨规范按有无自动触发时机分两类——A 类（有自动触发时机）：规范文档"触发时机"字段写明的时机到达时必须执行；M 类（无自动触发时机）：不预设发生时机，由人类工程师决定何时启用。**无论有无自动触发时机，任何肋骨规范都可随时由人类工程师手动触发。** 各规范的触发时机以具体文字直接写在该规范的 `规范.md` 的"触发时机"字段中；无自动触发时机的写"无自动触发时机——由人类工程师手动启用"，并可附典型启用场景或适用条件；触发时机提及脊椎流程阶段时，在文字中直接写明。
- **与脊椎流程的先后关系**：A 类再按产物与脊椎流程的先后关系分为两种，以编号前缀区分——**AF**（领先于脊椎流程：其产物是脊椎流程的输入依据）与 **AB**（落后于脊椎流程：其产物以脊椎产物为依据登记、维护，不作为脊椎流程的输入）。先后关系规则：AF 类规范的产物（如 AF02-需求基线）可以领先于脊椎流程中的对应文档；脊椎流程内部，前序阶段的产物可以领先于后续阶段；脊椎产物需要向需求基线对齐时，从阶段 S01 开始按阶段顺序逐个阶段对齐。
- **编号**：规范文件夹与同名产物文件夹以"类字母 + 两位数字-名称"命名（如 `AF01-提示词节点/`、`AB04-脊椎产物变更记录/`、`M01-部署和运维/`）；A 类（AF 与 AB 合算为一个序列）与 M 类各自从 01 起连续编号；新增规范在所属类内追加下一个序号。
- **日期时间文件夹**：肋骨产物中按日期时间组织的文件夹，命名统一为 `YYYY-MM-DD-HHMM`（如 `2026-09-16-1430`）。
- 实例预置十三份初始肋骨规范：
  - **AF01-提示词节点**：人类工程师每次发出提示词时必须执行——将每次提示词记录为一个节点（序号、日期时间、原文、备注），汇总于记录文件；
  - **AF02-需求基线**：人类工程师每次输入含有需求信息的提示词或文件时必须执行——先更新两份产物（需求总表只记最新状态、按项目结构索引；需求总表变更记录以日期时间为主索引、历史节点只增不改），再开展其他工作；全部需求的最根本依据，领先于脊椎流程中的需求文档；
  - **AB03-项目最新状态**：项目状态变化时必须执行——更新对应状态文档（三份：脊椎流程进展、肋骨规范进展、外骨骼实现情况）；只记最新状态，不记更新痕迹；产物文件夹随实例模板预置（见第 5 节）；
  - **AB04-脊椎产物变更记录**：任何脊椎产物发生变更时必须执行——变更结束时在唯一一份变更记录文档中追加一条记录（日期时间、变更的脊椎产物、变更内容、原因、回流检查结论）；
  - **AB05-需求追溯表**：随各阶段产物产生而持续维护——需求 → 功能 → 页面 → 模块 → 任务 → 用例的对照表；需求编号的权威来源是阶段 S01 的需求确认清单；
  - **AB06-美术素材备份**：每当项目中引用新的美术素材时必须执行——按日期时间文件夹备份素材原件与派生变体（脚本复现）并维护素材清单；
  - **M01-部署和运维**：无自动触发时机，由人类工程师手动启用——何时部署、何时运维由人类工程师决定；
  - **M02-修复和优化**：无自动触发时机，由人类工程师手动启用——每次会话产出一个日期时间文件夹，记录本次修复与优化历史；涉及功能修复须复测并记录结论；涉及脊椎产物改动时记录改动历史或写指针指向 AB04；
  - **M03-上架**：无自动触发时机，由人类工程师手动启用——仅商店分发形态的项目（移动 App、小程序等）适用；审核驳回的返工按回流条款处理，检查结论并入当次变更记录；
  - **M04-工作量评估**：无自动触发时机，由人类工程师手动启用（典型场景：阶段 S01 产物确认后首评，阶段 S03、S05 产物确认后复评）——按固定计算方法（页面/功能/数据模型/外部服务工作量 × 性能系数 × 平台端系数）评估大概工作量；仅供报价与宏观排期参考，不作为阶段 S06 的输入依据；
  - **M05-甲方原始文件**：无自动触发时机，由人类工程师手动触发——AI 创建一个以当前日期时间命名的文件夹，人类工程师手动将甲方提供的原始文件（素材包、设计稿、会议记录等）放入；
  - **M06-对外文档**：无自动触发时机，由人类工程师手动启用——管理供甲方阅读的三种文档（需求与功能文档、交付边界文档、技术栈文档）；MD 为权威版本、DOCX 为派生版本；按日期时间文件夹组织；项目内部禁止参考；
  - **M07-账号密码管理**：无自动触发时机，由人类工程师手动启用——集中登记项目所有正式与测试账号的账号密码（明文入库，适用前提：私有仓库）。

## 5. 项目最新状态（AB03）维护细则

`紫金产物/肋骨产物/AB03-项目最新状态/` 记录项目的最新状态，由 AI 维护、人类工程师阅读确认。其中"脊椎流程进展"是整个项目的宏观待办清单（见第 3 节），是 AI 与人类工程师对齐项目当前位置的首要依据。

产物文件夹下固定三份状态文档：

- `脊椎流程进展.md`：八个阶段的进展（未开始/进行中/已完成；阶段状态只有经人类工程师确认后才能标为"已完成"）；
- `肋骨规范进展.md`：各肋骨规范的执行进展（规范名、时间、所属阶段、产出位置、当前进展）；
- `外骨骼实现情况.md`：各模块合金文档与实施的对齐程度（仅合金文档/部分实施/已对齐）。

规则：

- 每份状态文档只记录最新状态，不记录任何更新痕迹——状态的历史变动不由本规范记录（脊椎产物的变更历史归 AB04-脊椎产物变更记录）。
- 更新时机（以下节点完成后即时更新，不得批量推迟）：
  1. 脊椎流程某阶段开始、或完成并经人类工程师确认后——更新"脊椎流程进展"；
  2. 肋骨规范每次执行或进展变化后——更新"肋骨规范进展"；
  3. 架构设计实施、模块实施或合金文档重构后——更新"外骨骼实现情况"；
  4. 升级紫金规范版本后——记录版本变化。
- 每次更新同时更新文档中的"最后更新"时间。
- 本肋骨的产物文件夹随实例模板预置（含三份空骨架），是"肋骨产物文件夹随首次产出创建"规则的例外。
